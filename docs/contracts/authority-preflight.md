# Authority card view

`await prepareNativeAuthorityCard(context)` produces a read-only native preflight for exact requested configuration records. `record-coverage` checks current signer eligibility, coordinate coverage and the existing widening witness rule. `admission` additionally invokes the same structured wire, standing-pin, same-lot withdrawal, destination ownership, fork, alias, existing-reading, withdrawn-coordinate and demand checks used by the native admission path. Root and child destinations use their actual authenticated standing. An `allow` covers only this named configuration preflight; the eventual act still verifies its actual signatures, current authority and commit conditions. It never signs, commits, publishes or runs a requested action.

The receiver supplies the Root location and native instrument. Both public operations are asynchronous and retain the existing native Root authority protection while inspecting evidence. The protection is released before the promise settles, including refusals, and nested protected calls reuse their real held protection. Prospective child inspection preserves the caller's preview state and keeps nested Root previews separate. Every call supplies a `{name, unit, now}` clock. The native context may omit `authorityEpoch` to select the receiver's current authenticated admission epoch; an explicit epoch remains an expected-state condition. The wire request still requires an explicit epoch. Current Root history is freshly authenticated from the original bootstrap anchor; grant digests supplied in request JSON establish nothing. Root history and selected lock bytes must remain unchanged throughout preparation. Operational elapsed-time measurements in existing demand/fold code continue using the actual host clock. They are not substituted for card freshness and are not frozen to the supplied semantic time.

The `catalog` and `standingContract` fields are the exact digests of the shipped refusal catalog and standing contract, read by the existing installed-contract helper. Policy, coverage, budget and judgment digests commit semantic context; they do not name invented files. The card uses the Topos authority-card format and `authorityCardAnswer`. Its coverage commitment binds the real Root location, selected place, key, authenticated current grants and exact action identities. Its snapshot binds the selected lock bytes. Answering reruns the native checks and verifies the reconstructed statement and evidence; it accepts no consumer-provided judgment callback. Grant retirement invalidates a card even when child lock bytes remain unchanged. An expired or obsolete card returns `card-stale`; an action absent from the card returns `not-in-card`. Parsed card shape alone cannot establish authority.

`allow`, `ask` and `deny` preserve the existing check outcomes. `ask` names the missing signatures, widening witnesses, existing readings or unpaid demands. Named native authority, wire, pin, placement, fork, withdrawal and demand refusals produce `deny`. Missing bounded admission evidence remains `ask` with its exact request identity. New demands remain owed until their native judgment is paid. A declared reading-witness policy uses the same witness-admission hook for the view and the act; legacy witnessing remains unchanged when no such policy is selected. Typed-object admission, execution and unrelated aggregate actions are outside this configuration contract and refuse explicitly.

## Request selection

`fold --as authority-card@<scope>` selects exactly one currently admitted Root record at `<scope>` with `form=alphabet`, `role=writes`, `measure=authority-card-request` and a SHA-256 digest in `value`. Two admitted interval records `<scope>/bytes` and `<scope>/items`, each `role=writes` and `value=0..N`, bound the request. The receiver reads local CAS bytes with the declared byte bound before decoding or hashing, verifies the selected digest, and calls `parseNativeAuthorityCardRequest`. It never resolves or executes an offered provider for this view.

The request document contains exactly `profile`, `place`, `key`, `authorityEpoch`, `clock`, `horizon`, `limits` and `actions`. The profile is `native-authority-card-request/1`. `place` is `.` or a declared relative child. `limits` contains positive finite `bytes` and `items`, neither larger than the admitted request policy. Every action contains exactly `kind` (`record-coverage` or `admission`) and `records` (wire-line strings). Clock contains exactly `name`, `unit` and `now`; horizon contains exactly `clock`, `unit`, `from` and `through`. Requested key names, record signatures and clocks are data checked against the current receiver context. The request cannot supply a Root path, store, instrument, trust anchor or private key. Extra `root` or `instrument` fields, unsupported actions, invalid clocks, unbounded input and digest mismatches refuse.

`await answerNativeAuthorityCard(card, requestIdentity, context)` uses the same trusted receiver inputs and fresh explicit request snapshot. Consumers use `nativeAuthorityRequestIdentity(action)` to name an exact action; they do not reconstruct grants or infer permission from a card's shape. All byte/item limits are finite, and preparation persists no admission result or proof cache.

## Current receiver epoch

The native authority-card preparation selects the receiving Root's current local admission epoch when `authorityEpoch` is omitted. It uses the same freshly read history, original bootstrap anchor, authority evaluator and Root protection as explicit-epoch preparation. Supplying `authorityEpoch` remains an expected-state condition: a different actual local epoch refuses with `authority-preflight/stale-epoch`. No second authority evaluator or inference from a view is introduced.

Imported evidence has its own origin and clock. A sender at epoch 6 does not advance a receiver at epoch 3. A local import receipt can have a later act epoch without changing the Root admission-history epoch used by this preflight. Neither evidence maxima nor filesystem metadata select the receiver's authority. Evidence is not discarded or called obsolete merely because its origin uses a different clock.

The receiver supplies an explicit semantic clock, horizon, key, selected place, instrument and finite byte/item budgets. Missing authority or an invalid context refuses; no wall-clock substitution is made for semantic time. The clock is a receiver input, not proof of externally certified time. Card fields retain their existing meaning and authenticated interpretation; a parsed shape or a returned digest alone proves no authority.

Preparation retains the existing change detection and Root protection. Answering a card reconstructs the current judgment and compares its existing state, policy, coverage and evidence commitments. A changed grant, altered statement or transplanted card cannot yield the previous affirmative judgment. Diagnostics use existing bounded refusal records. A card grants no later action: signatures, current authority and commit conditions are still checked at the act.

Only the native JavaScript call gains current-state acquisition by omission. The `native-authority-card-request/1` wire request still requires an explicit integer `authorityEpoch`; its parser, admitted request selection and CLI/host view policy remain unchanged. No new verb, wire form, clock profile or runtime dependency is added. Current selection must not be used to bypass the revalidation of an already presented card.

Migration: prepare and answer through the existing public native authority-card functions; do not calculate a receiver epoch from `evidence`. An existing caller supplying a valid expected epoch retains the same result and stale-state behavior. Exact API declarations and installed acceptance must be verified before selecting the implementation for delivery.

The eight neutral vectors in `vectors/preflight/receiver-current.json` cover current/explicit agreement, sender/receiver separation, missing or altered authority, explicit clocks, transplanted cards, retired grants, mutation during preparation and preserved explicit/wire checks. They run in two unrelated fixture domains. The existing authority-card view and dependency-withdrawal regressions remain in force. A successful fixture run is not a paid Root receipt or release approval.
